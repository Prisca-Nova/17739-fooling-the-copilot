# Project check-in: 2026-10-30

**Fooling the Copilot: do an LLM's own routine QA edits make it reverse its security verdict?**
Prisca & Eileen · 17-739/18-739

## 1. Question and method (unchanged from the proposal)

Give an LLM a small JavaScript program it correctly flags as **vulnerable**, ask the same LLM for an
ordinary QA edit (documentation, logging, refactor, error handling, input validation), then ask again
whether the code is vulnerable. Every flip to "safe" is checked by **running the edited code**, to
separate a genuine miss from an edit that really fixed the bug.

## 3. Result 1: baseline, `qwen2.5-coder:7b` (free, local)

102 stubs × 3 repeats, default detection prompt:

| | Vulnerable → VULNERABLE (recall) | Safe → SAFE (specificity) |
|---|---|---|
| XSS | 51/51 | 7/51 |
| Command injection | 51/51 | 0/51 |
| Path traversal | 50/51 | 2/51 |
| **All** | **152/153 (99%)** | **9/153 (6%)** |

- The 7B model calls almost everything vulnerable (precision ≈ 51%, about what "always vulnerable" scores).
  This is the failure mode the half-safe design was built to expose.
- **Prompt priming ruled out:** a neutral prompt (no security persona, no source/sink hint) gave the same
  picture (recall 98%, specificity 4%; 97/102 identical verdicts).
- Reading the explanations: the model *notices* sanitizers but dismisses them ("not sufficient"), or misreads code.
- 8/102 stubs changed verdict across repeats, almost all safe ones.
